## Цель для обучающегося

Обучающийся должен понимать, как в области Policy бизнес-намерение превращается в сетевую политику вида «источник — контракт (permit/deny) — назначение» между группами (Employees → BYOD, HR → Development_Servers…) и чем IP-политика доступа похожа на знакомый ACL (источник, контракт, назначение, направление); и как область Assurance показывает здоровье сети (проценты по ролям устройств, проводным и беспроводным клиентам), ранжирует проблемы (P1…), а для каждой предлагает **пошаговую диагностику с кнопкой Run**, которая выполняет на устройстве обычные команды `show` и трактует результат — то самое «контроль → обратная связь» из цикла IBN.

Текст 14.6.5 даёт только определения областей Policy («автоматизируют и упрощают управление…») и Assurance («упреждающий мониторинг…»). Видео добавляет: вид политик TrustSec (18 групповых политик, 37 масштабируемых групп, 2 виртуальные сети), структуру политики (Sources / Contract / Destinations), форму IP-политики с направлением, панель здоровья с цифрами (83 % устройств, 98 % проводных, 90 % беспроводных, 249 активных), конкретные P1-проблемы фабрики SD-Access и, главное, **реальный вывод IOS XE** с коммутатора `border_cp_sda.local`, который контроллер собрал автоматически — мост между GUI контроллера и CLI, изученным в курсе.

## Предложение по пересборке

**Формат:** видео с генерированным голосом (код-рендер; макет GUI контроллера + настоящий вывод CLI), ~2:30. Самое ценное — сцена, где контроллер выполняет `show`-команды и трактует вывод: её стоит сделать двухоконной (слева «карточка проблемы» контроллера, справа терминал коммутатора), а в симуляторе дать обучающемуся выполнить те же команды вручную и сравнить с «вердиктом» контроллера.

**Сцены (сцена → визуал → озвучка):**
1. Макет «Политики»: плитки 18 групповых политик / 37 групп; карточка `Employees → permit → BYOD` → «Политика — это намерение: кто, к чему, что разрешено».
2. Карточка «IP-политика»: Source · Contract · Destination · Direction рядом со строкой ACL `permit ip 10.1.0.0 0.0.255.255 10.2.0.0 0.0.255.255` → «Это тот же ACL, только контроллер сам разнесёт его по устройствам».
3. Макет «Здоровье»: 83 % / 98 % / 90 %, список Top issues с P1 «Fabric Reachability Failure» → «Контроль: контроллер сам ранжирует проблемы».
4. Карточка проблемы с четырьмя действиями; нажатие Run → справа терминал `border_cp_sda#` с `show ip route 192.168.139.168`, `show ip cef …`, `show eigrp address-family ipv4 neighbors`; галочки «Success» появляются по мере вывода → «Контроллер выполняет те же команды, что и вы, и читает ответ».
5. Итог: петля «проблема → проверка → вывод CLI → вердикт → (эскалация)» → «Автоматизация не отменяет понимание CLI — она его использует».

**Активы:** макеты плиток/карточек контроллера; рамка терминала; таблица «IP-политика ↔ ACL».

**Замечания к оригиналу (исправить при пересборке):**
- Диктор: «checks IS-IS — exists, OSPF — good to go»: на самом деле вывод `show isis neighbors` и `show ospf neighbor` **пуст** (соседей нет); «Success» означает лишь, что команда выполнилась. Смежность есть только по EIGRP — в пересборке сказать это явно, это важный урок чтения вывода.
- Все проверки «успешны», а проблема (потеря связи с ISE) не решена — ролик заканчивается на «обратитесь в TAC». В пересборке довести диагностику до вывода (см. `ping` выше) или честно сказать, что контроллер исключил маршрутизацию и сузил область поиска.
- Терминология: «IP-based access control takes you back to IPv4 ACL days» — полезно, но стоит добавить, что групповые политики (TrustSec/SGT) не зависят от IP-адресов — в этом их смысл.
- DNA Center → Catalyst Center; страницы Policy/Assurance в новых версиях перестроены — макет, а не скриншоты.
- Реплики «HR с BYOD — звучит страшно», «Cisco DNA, поможешь? — Конечно» — убрать.
