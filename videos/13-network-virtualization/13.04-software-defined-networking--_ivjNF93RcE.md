## Цель для обучающегося

Обучающийся должен понимать, что такое программируемая сеть: какие протоколы (OpenFlow, NETCONF, RESTCONF), языки (C/C++/Java, Python/Ruby/Lua), модели данных (YANG), разметка (XML) и API (REST) используются для программирования сети; в чём суть SDN — отделение уровня управления (control plane) от уровня передачи данных (data/forwarding plane) и вынос его в централизованный контроллер; что такое сетевой контроллер и как он связывает приложение/политику с устройствами (на примерах OpenDaylight и Cisco APIC-EM).

Текст темы (13.4.2–13.4.4) подробно объясняет уровни управления/передачи данных (с CEF), уровень управления устройством (SSH/SNMP), компоненты SDN (OpenFlow, OpenStack, I2RS, TRILL, FabricPath, SPB), сравнение архитектур и полную структуру SDN с «северными» и «южными» API (рис. 13.4.4-2). Видео добавляет **инвентарь инструментов сетевого программирования** (протоколы, языки, YANG, XML, REST) — в тексте их нет, они появятся в модуле 14 — и **роль контроллера с конкретными примерами** (OpenDaylight как открытая платформа контроллера; стек Cisco APIC-EM «Application → Policy → SDN Controller → OpenFlow → устройства»), а также первое упоминание Cisco ACI (ANP, APIC, Nexus 9000), которое развивается в 13.5.

## Предложение по пересборке

**Формат:** анимация Figma (≤ 60 с) для ядра темы — «разделение уровней и контроллер» — плюс **текст + иллюстрация** для инвентаря инструментов (таблица «протоколы / языки / модели данных / API» в 13.4.1 или в начале модуля 14). Оригинальные 5 минут держатся на четырёх текстовых слайдах; переносить их в видео нет смысла.

**Сцены анимации (сцена → визуал → озвучка):**
1. Три коммутатора в ряд, у каждого два блока: «уровень управления» (оранжевый) над «уровнем передачи данных» (голубой); на каждый по очереди «прилетает» иконка CLI → «В традиционной сети мозг — уровень управления — есть у каждого устройства, и настраивать нужно каждое».
2. Оранжевые блоки отрываются от устройств, сливаются в один блок «SDN-контроллер» сверху; вниз к устройствам протягиваются линии с подписью «OpenFlow (южный API)» → «SDN отделяет уровень управления и выносит его в контроллер; устройства только пересылают трафик».
3. Над контроллером появляется блок «Приложение / политика», стрелка «REST (северный API)»; примеры подписями: OpenDaylight, Cisco APIC-EM → Catalyst Center → «Контроллер — программируемая точка автоматизации: приложение задаёт политику, контроллер программирует сеть».
4. (опц.) Карточка «Инструменты»: OpenFlow · NETCONF · RESTCONF · YANG · XML/JSON · REST · Python.

**Активы для отрисовки:** блоки control/data plane, иконка контроллера (сервер), иконка приложения, подписи северного/южного API (совместимы с рис. 13.4.4-2 курса).

**Замечания к оригиналу (исправить при пересборке):**
- «Сетевой контроллер — аппаратное устройство» (3:30): контроллер — программное обеспечение (ПО OpenDaylight, виртуальная машина или appliance); аппаратность не является его признаком.
- Слайд 12 показывает OpenFlow как южный интерфейс APIC-EM/ACI. ACI использует OpFlex и собственные механизмы APIC, а APIC-EM управлял классическими IOS-устройствами через CLI/SNMP/NETCONF, а не OpenFlow.
- Cisco onePK снят с производства (2015), APIC-EM заменён на DNA Center (ныне Catalyst Center) — в пересборке называть актуальные продукты или говорить обобщённо.
- APIC-EM — контроллер кампусной сети, а ACI — фабрика ЦОД с контроллером APIC и Nexus 9000; видео (и текст 13.5.2) смешивают их — стоит явно разделить.
- Слайд 4 относит «Java» к «Architectures and APIs» рядом с REST — лучше заменить на «REST, gRPC/gNMI» или оставить только REST.
